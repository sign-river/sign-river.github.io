# 优化博客文章内容

## 目标

处理用户指定路径的已有文章正文：在不改变事实边界的前提下，优化文章结构、补全表达、改善段落衔接、统一术语和美化措辞。用户自己提供的内容可能比较草稿化，应负责整理成清晰、完整、可发布的文章，但不能凭空编造用户没有提供的操作、数据、结论或经验。

## 必须遵守的内容边界

1. 只处理用户指定的文章；不要顺手修改相关文章、分类统计或其他文件。
2. 默认保持 Front Matter 不变。只有用户明确要求时，才修改标题、描述、分类、标签、日期、slug 或 `draft`。
3. 正文标题从 `##` 开始，保持仓库规定的标题层级和编号风格。
4. 操作步骤中的按钮、选项名称使用加粗；命令、路径、文件名使用行内代码；注意事项使用引用块。
5. 可以重排段落和小节，可以将零散句子整理为步骤、列表、表格或说明段，但不得改变用户表达的事实含义。
6. 对缺少依据的内容使用中性表达或保留待补充占位，不要假设版本号、兼容性、性能、成功率、错误原因或安全结论。
7. 如果文章明显缺少关键上下文，只补充结构性过渡和表达，不擅自补充技术事实；必要时在完成报告中列出待用户确认项。

## 图片引用保护规则

图片引用是不可修改的受保护内容。优化前必须先记录文章中所有图片引用的完整文本，并在优化后逐一核对。

- 不修改图片标签、HTML 属性、Markdown 图片语法、图片路径、文件名、锚点地址、`target`、`alt` 或样式。
- 不把 HTML 图片引用改成 Markdown，也不把 Markdown 图片引用改成 HTML。
- 不移动图片到其他位置，除非用户明确要求调整图片位置。
- 不删除、复制或合并图片引用。
- 图片前后的说明必须保持一一对应：每张图片应继续紧邻其对应描述；若重写描述，只能润色原描述，不能把描述改成另一张图片的说明。
- 如果图片与正文说明的对应关系本来就不清楚，不要猜测；在报告中指出需要用户确认。

推荐的保护检查方式：

1. 优化前提取所有包含图片引用的完整行或 HTML 块。
2. 编辑正文时将图片块视为不可编辑区。
3. 优化后核对图片引用数量、路径和完整文本完全一致。
4. 检查每个图片块前后的描述是否仍然对应原来的图片。

## 工作流程

1. 先运行 `git status --short`，识别用户已有改动并保护它们。
2. 读取用户指定的文章完整内容；如果是项目文档或专题文章，同时读取其所在结构需要的规范文档。
3. 完整读取：
   - `docs/文章模板.md`
   - `docs/分类标签规范.md`
   - `docs/AI辅助写作指南.md`
4. 统计并记录 Front Matter、正文标题、图片引用数量和图片说明。
5. 分析文章当前问题：结构重复、步骤顺序不清、段落跳跃、表达口语化、术语不统一、缺少前置条件或验证结果等。
6. 在保护 Front Matter 和图片引用的前提下优化正文：
   - 先明确文章目标、适用对象和前置条件。
   - 按任务顺序重新组织小节。
   - 把草稿句整理为完整句子和可执行步骤。
   - 补充必要的过渡、结果和验证说明，但只使用用户已提供或文章中已有的信息。
   - 删除重复、空泛和与主题无关的表述。
   - 保持中文表达自然、简洁、清晰，避免过度营销或夸大。
7. 写入前再次读取文件当前内容，避免覆盖用户在处理中新增的编辑。
8. 写入后执行保护检查：
   - Front Matter 未被意外修改。
   - 图片引用数量一致。
   - 每个图片引用的完整文本一致。
   - 图片路径和文件名仍指向实际存在的文件。
   - 图片与描述保持一一对应。
   - `git diff --check` 通过。
9. 条件允许时运行 `hugo --gc --minify`，确认构建没有错误。

## 何时需要询问

只有在无法安全编辑时才询问，例如：

- 用户未提供文章路径，且仓库中无法唯一确定目标文件。
- 文章存在多个图片说明，无法判断某段描述对应哪张图片。
- 用户要求“完善内容”，但现有草稿没有足够事实支撑核心章节。
- 目标文件存在未提交的编辑，继续写入可能覆盖用户刚刚修改的内容。

如果只是语言、结构或段落衔接问题，应直接优化，不要因为文章草稿化而反复询问。

## 输出格式

完成后用中文报告：

1. 优化的文章绝对路径。
2. 优化了哪些方面：结构、步骤、段落、术语、表达等。
3. 图片引用保护检查结果：原数量、现数量、路径和完整引用是否一致。
4. Hugo 或其他检查结果。
5. 仍需用户确认或补充的事实、图片说明或章节。

如果没有实际写入，必须说明原因，不要假装优化完成。
